# LLM文字起こし整備ワークフロー 設計

作成: 2026-07-08
ステータス: 承認済み (運用しながら改善する前提)

## 背景と目的

「子育てのラジオ Teacher Teacher」のLISTEN文字起こしは、公開時点では自動文字起こしのままの品質。
これを整備すると、あとから読みに来た人の体験がよくなる (ストック的価値)。
人力のみの運用では継続が難しくなったため、LLMを組み込んだワークフローに移行する。

品質の目安:

- 自動文字起こしそのまま: 50
- 人間がじっくり整備した状態: 100
- LLM整備の目標: 80

すでに公開されている50の状態を機械で80に引き上げ、100にしたい回だけ人間が磨く。

## 役割分担 (品質の階段)

| 段階 | 担当 | 品質 | 作業内容 |
|---|---|---|---|
| 自動文字起こし | LISTEN | 50 | 公開された時点の状態 |
| 話者登録 + ざっと確認 | 人間 (5分/本) | 60 | LISTENエディタで話者登録し、進行管理表を「作業待ち」に |
| LLM整備 | コンピュータ | 80 | 本設計のパイプライン |
| じっくり磨き | 人間 (任意) | 100 | やりたい回だけ。Discordレポートが入口 |

鍵となる分業: LISTENの話者分離 + 人間の話者登録により、機械に最も難しい
「誰が喋っているか」問題が解決済みの状態でLLMに渡る。LLMの仕事は
「ガイドラインに沿ったテキスト校正」という得意分野に限定される。

## フェーズB: 対話型パイプライン (最初に作るもの)

Claude Codeセッションで1エピソードずつ処理する。エントリポイントはリポジトリ内スキル (`/seibi` 想定)。

### 処理フロー

1. **再取得**: 対象エピソードのVTTをLISTENから再ダウンロードする。
   話者登録済みの最新版を取るため、リポジトリ内のファイルは信用しない。
   整備前のVTTは `transcript.original.vtt` として残し、diffの基準にする。
2. **LLM校正**: `proofreading_guide.md` に従ってテキストのみ編集する。
   - 制約: タイムスタンプ・cue構造は不変。話者タグは原則維持
   - 長いエピソードはチャンク分割し、サブエージェント (Sonnet想定) に並列処理させる
   - 話者割り当てに文脈上の違和感があるcueは、明らかなものは修正、
     確信が持てないものは「疑義リスト」として報告に回す
3. **機械検証** (`validate_vtt.py` を新規作成): 検証を通らない限り先に進まない。
   - VTTとして構文的に正しいか
   - タイムスタンプ・cue数が原本と一致するか
   - 話者名がallowlist (レギュラー + そのエピソードの登録話者) 内か
   - cueごとのテキスト変更量が閾値内か (捏造・大幅欠落の検出)
4. **レポート生成**: `report.md` をエピソードディレクトリに保存。
   - カテゴリ別修正件数 (フィラー削除、句読点、表記統一、誤認識修正、話者修正)
   - 注目すべき修正の抜粋
   - 話者疑義リスト (直さなかった箇所と理由)
5. **人間チェック**: セッション上でdiffとレポートを確認し、フィードバックがあれば反映する。
6. **アップロード**: junebokuがLISTENのVTTアップロード機能で反映する (フェーズBでは手動)。
7. **通知**: DiscordスレッドにWebhookでレポート要約を投稿する。
   コミュニティの人が「ここは変だな」と気づいたらLISTEN上で直しに行ける。
8. **記録**: git commit (整備前後の差分が蓄積され、ガイドライン精緻化の材料になる)。
   進行管理表のはひステータスを「いったん納品」に更新する (gws経由、書き込みなので実行前に確認)。

### 明示しておく制約

- **音声イベント補記** (`（手を叩く音）` 等) はLLMには不可能 (音声を聞けない)。
  80点の範囲に含めず、人間が100に磨くときの領域とする。
- **誤認識の修正**は文脈から明らかなものに限る。番組用語集 (『コンプリメント』
  『イエナプラン』等の固有名詞辞書) をリポジトリに置き、参照させて精度を上げる。

### エラーハンドリング

- 機械検証に失敗した場合: アップロード対象にせず、失敗内容をセッションで報告する
- Discord投稿の失敗: 致命的でない。手動で投稿できるようレポート本文を提示する
- スプレッドシート更新の失敗: 致命的でない。手動更新を依頼する

## フェーズC: 自動化への段階 (ロードマップ)

- **C1**: cronで「新着 + 作業待ち」を検知して無人整備し、レポートをDiscordへ投稿。
  アップロードのみjunebokuが承認する。
- **C2**: LISTEN側にVTTアップロードAPI (トークン認証) を実装し、完全無人化。
  人間はDiscordレポートを事後の目として使い、気になったら直しに行く。

移行判断: フェーズBの最初の10〜20本が品質見極めの評価データとなる。
フィードバックは `proofreading_guide.md` と用語集に還元し、安定したらC1へ進む。

## バックログの扱い

未整備の約86本 (保留51 + 作業待ち21 + 未分類14) も、人間の話者登録さえ済めば
同じパイプラインに流せる。新着優先で運用を安定させたのち、ペースを決めて消化する。

## テスト方針

- `validate_vtt.py` は単体テストを持つ (正常系 + タイムスタンプ改変・話者逸脱・過剰変更の検出)
- LLM校正の品質評価は、フェーズB序盤の人間レビューそのものを評価プロセスとする
